# 隐私与合规检查报告

**检查日期**：2026-09-11
**检查范围**：tsm-hub 项目（Go 后端 + Angular 前端）
**检查维度**：API 密钥安全、数据隐私、日志安全、认证授权、输入验证、传输安全、合规性文档

---

## 一、总体评价

项目在隐私和合规方面整体做得**比较扎实**，特别是在 Token Key 哈希存储、日志不记录请求内容、路径遍历防护、SSRF 防护、Docker 沙箱等方面都有完善的实现。SECURITY.md 文档也比较全面。

但仍有 **2 个高风险问题** 和 **3 个中风险问题** 需要关注，主要集中在传输安全和密钥存储方面。

## 三、发现的问题 ⚠️

### P0 - 高风险（建议尽快修复）

#### 问题 1：网关本身不支持 TLS/HTTPS

**严重程度**：高
**影响范围**：所有 API 通信
**问题描述**：
- 服务器启动代码（cmd/tsm-hub/main.go）和配置结构中均未发现 TLS 相关选项
- 网关只支持 HTTP，不支持 HTTPS/TLS
- API 密钥（Authorization 头）和用户数据在网络上以明文传输
- 在非可信网络环境中，存在中间人攻击和密钥窃取风险

**修复建议**：
1. **短期（推荐）**：在生产环境中使用反向代理（Nginx、Caddy、Traefik）提供 HTTPS 终端，反向代理到网关的 HTTP 端口
2. **长期**：在网关中增加 TLS 支持，配置项包括：
   - `tls.cert_file` - 证书文件路径
   - `tls.key_file` - 私钥文件路径
   - `tls.enabled` - 是否启用 TLS
   - 使用 `http.Server.ListenAndServeTLS()` 启动

**文档补充**：在 SECURITY.md 和 README.md 中明确说明生产环境必须使用 HTTPS，并提供反向代理配置示例。

---

#### 问题 2：上游 Provider API Key 明文存储

**严重程度**：高
**影响范围**：所有上游 Provider 配置
**问题描述**：
- Provider 的 API Key 以明文形式存储在 config.json 中
- 虽然文档建议使用 `env:` 前缀引用环境变量，但默认支持明文填写
- 如果配置文件泄露（备份泄露、误提交 git、服务器被入侵），所有上游 API Key 都会泄露
- config.json 权限建议为 600，但这依赖用户手动设置，程序未强制

**修复建议**：
1. **短期**：
   - 在文档中强烈建议使用 `env:` 前缀引用环境变量
   - 启动时检查 config.json 权限，如果不是 600 则发出警告
   - 管理台创建/修改 Provider 时，默认提示使用环境变量
2. **长期**：
   - 增加加密存储选项，使用 AES-256-GCM 加密 API Key，主密钥从环境变量或密钥管理服务获取
   - 或者集成外部密钥管理服务（HashiCorp Vault、AWS Secrets Manager 等）

### P1 - 中风险（建议下个版本修复）

#### 问题 3：Gemini 适配器在 URL 中传递 API Key

**严重程度**：中
**影响范围**：Google Gemini 适配器
**问题描述**：
- `internal/proxy/adapter/adapter_gemini.go:31,34` 中，API Key 通过 URL query 参数 `key=` 传递
- URL 通常会被记录在各种日志中（反向代理访问日志、上游服务器日志、网络设备日志等）
- 可能导致 API Key 在日志中泄露

**修复建议**：
1. 检查 Gemini API 是否支持通过请求头传递 API Key（如 `x-goog-api-key`）
2. 如果支持，改为通过请求头传递
3. 如果必须通过 URL 传递，确保：
   - 网关自身的访问日志不记录完整 URL（或对 key 参数脱敏）
   - 在文档中说明此风险

---

#### 问题 4：缺少 CORS 配置

**严重程度**：中
**影响范围**：浏览器端直接调用网关的场景
**问题描述**：
- 代码中未发现 CORS（跨域资源共享）相关配置
- 如果网关需要被浏览器端（前端应用、第三方网页）直接调用，需要配置 CORS 策略
- 缺少 CORS 配置可能导致：
  - 浏览器端调用被拒绝（默认情况下 Go 的 net/http 不发送 CORS 头）
  - 或者如果用户自行配置了过于宽松的 CORS（`Access-Control-Allow-Origin: *`），可能导致跨域安全风险

**修复建议**：
1. 增加 CORS 配置项：
   - `cors.allowed_origins` - 允许的源列表
   - `cors.allowed_methods` - 允许的 HTTP 方法
   - `cors.allowed_headers` - 允许的请求头
   - `cors.allow_credentials` - 是否允许携带凭证
2. 默认配置为安全的保守策略（如只允许特定源，不使用 `*`）
3. 在文档中说明 CORS 配置的安全注意事项

---

#### 问题 5：缺少隐私政策/数据处理协议（DPA）文档

**严重程度**：中
**影响范围**：合规性
**问题描述**：
- docs 目录中只有 ARCHITECTURE.md、SECURITY.md、TODO.md
- 缺少隐私政策（Privacy Policy）和数据处理协议（Data Processing Agreement, DPA）
- 如果项目用于处理用户数据（特别是个人数据），根据 GDPR、个人信息保护法等法规，可能需要提供相关文档
- 缺少数据主体权利说明（访问权、更正权、删除权、可携带权等）

**修复建议**：
1. 增加 `docs/PRIVACY.md` - 隐私政策，说明：
   - 收集哪些数据
   - 数据用途
   - 数据保留期限
   - 数据主体权利
   - 数据安全措施
   - 联系方式
2. 增加 `docs/DPA.md` - 数据处理协议模板（如果项目作为数据处理者）
3. 在 README.md 中链接到这些文档

### P2 - 低风险/建议（可纳入长期规划）

#### 问题 6：管理接口缺少速率限制

**严重程度**：低
**问题描述**：未发现针对管理接口（/api/admin/*）的速率限制配置，可能存在 admin token 暴力破解风险。
**建议**：增加管理接口的速率限制（如每分钟最多 10 次登录尝试），失败多次后临时锁定 IP。

#### 问题 7：敏感操作缺少二次确认/请求签名

**严重程度**：低
**问题描述**：创建 Key、删除 Provider、修改配置等敏感操作只有 admin token 认证，缺少二次确认或请求签名机制。
**建议**：对于高风险操作（如删除所有数据、修改 admin token），增加二次确认机制。

#### 问题 8：前端 34 处 `any` 类型

**严重程度**：低
**问题描述**：前端代码中有 34 处使用 `any` 类型，可能导致类型不安全。
**建议**：逐步替换为具体类型，提升类型安全。

#### 问题 9：配置文件备份安全未在文档中强调

**严重程度**：低
**问题描述**：SECURITY.md 中提到了 config.json 权限，但未强调备份文件的安全。
**建议**：在文档中增加配置文件备份的安全注意事项（加密备份、限制备份访问权限等）。

#### 问题 10：依赖定期更新机制

**严重程度**：低
**问题描述**：未发现依赖定期更新的自动化机制。
**建议**：增加 Dependabot 或类似工具，定期检查依赖更新，及时修复已知漏洞。

## 六、总结

tsm-hub 项目在隐私和合规方面的基础**相当扎实**，特别是在 Token Key 安全、数据最小化、注入防护、沙箱隔离等方面都有完善的实现。SECURITY.md 文档也比较全面，说明项目有较好的安全意识。

**最需要关注的两个高风险问题**是：
1. 网关本身不支持 TLS/HTTPS —— 这是生产环境的基本安全要求
2. 上游 Provider API Key 明文存储 —— 配置文件泄露会导致所有上游密钥泄露

这两个问题都可以通过**文档引导 + 最佳实践**在短期内缓解（使用反向代理提供 HTTPS、使用环境变量引用密钥），长期可以在产品中增加原生支持。

整体评价：**良好（B+）**，修复 P0 问题后可达到**优秀（A-）**。
